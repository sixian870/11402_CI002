# UVa 540 - Team Queue

## 題目簡述

在一個常規的排隊系統（Queue）中，新加入的人一律必須排在整個隊伍的最後方。但在一個 **Team Queue（團隊排隊）** 系統中，排隊的元素各自屬於某個特定的團隊（Team）。
當一個新元素準備進入排隊時，它會遵循以下特殊的「插隊」規則：
1. **團隊有隊友**：如果目前排隊的隊伍中，**已經有和他屬於同一個團隊的隊友在排隊**，那麼這個新元素可以直接插隊，排在該團隊所有隊友的**最後方**（但仍在其他團隊之前）。
2. **團隊無隊友**：如果目前隊伍中沒有任何同團隊的隊友，新元素就只能乖乖排在整個排隊隊伍的**最後方**。

當進行移出隊伍操作（DEQUEUE）時，依然遵循先進先出（FIFO）原則，直接移出排在整個隊伍最前面的元素。<br>
當輸入的團隊總數 $T = 0$ 時，代表輸入結束。每一組 Scenario 的輸出之間必須以一個空行（Blank line）隔開。

**Sample Input**：

  **2** $\rightarrow$ 第一組測試資料，共有 $T = 2$ 個團隊。<br>
  **3 101 102 103** $\rightarrow$ 團隊 0 有 3 個人，成員編號為 101, 102, 103。<br>
  **3 201 202 203** $\rightarrow$ 團隊 1 有 3 個人，成員編號為 201, 202, 203。<br>
  **ENQUEUE 101** $\rightarrow$ 101 進隊。<br>
  **ENQUEUE 201** $\rightarrow$ 201 進隊。<br>
  **ENQUEUE 102** $\rightarrow$ 102 進隊（有隊友 101，插隊到 101 後方）。<br>
  **DEQUEUE**<br>
  **STOP** $\rightarrow$ 當讀取到指令為 "STOP" 時，代表該組測資結束。<br>
  **0** $\rightarrow$ 輸入結束標記。

**Sample Output**：

  **Scenario #1**<br>
  **101** $\rightarrow$ 第一個被移出隊伍的元素。<br>
  <br> $\rightarrow$ **核心注意：每組 Scenario 的輸出之間必須精確夾帶一個空行。**


## 解題思路與雙層佇列結構

### 核心觀念：團隊ID映射與雙層先進先出模型（Composite Queue / Double-Layer Queue）
這道題目的本質是**多維排隊系統的模擬與高階資料結構設計**。
如果只使用一個單一的 `std::queue` 或 `std::vector`，在每次新元素入隊時都要從頭到尾掃描尋找隊友，時間複雜度會直接退化到 $\mathcal{O}(N)$，進而引發超時。<br>
為了解決這個問題，最佳的資工實作手法是將整個排隊系統拆解為 **「雙層佇列（Double-Layer Queue）」** 的複合架構：

1. **團隊成員映射表（`team_map`）**：
   利用 `std::map<int, int>` 或者是直接開闢一個大陣列作為雜湊表，在讀入數據時，將「成員編號 `m`」映射至其所屬的「團隊 ID `i`」（即 `team_map[m] = i`）。如此一來，任何新成員抵達時，都能在 $\mathcal{O}(1)$ 常數時間內辨識出他是哪一隊的。
2. **主佇列（`main`）**：
   這是一個儲存**「團隊 ID」**的佇列（`queue<int> main`），用來管理目前碼頭上有哪些團隊在排隊，以及這些團隊之間的先後順序。
3. **小團隊佇列陣列（`team[]`）**：
   為每個團隊各自獨立開闢一個獨立的排隊佇列（`queue<int> team[1005]`）。`team[teamID]` 內部儲存的才是**「實體成員編號」**，負責記錄該小團隊內部的隊友排隊順序。

### 核心操作模擬
* **入隊（ENQUEUE x）**：

  先查出團隊 ID：`teamID = team_map[x]`。

  * 若 `team[teamID]` 為空，代表目前整個隊伍中**沒有他的隊友**。此時他身為隊長，必須先把他的團隊 ID 推入主佇列：`main.push(teamID)`，隨後再將自己推入自己的小團隊：`team[teamID].push(x)`。
  * 若 `team[teamID]` 不為空，代表**已有隊友在場**。他不需驚動主佇列，直接插隊推入小團隊末尾即可：`team[teamID].push(x)`。

* **出隊（DEQUEUE）**：

  先看主佇列最前面的團隊是誰：`front_team = main.front()`。<br>
  印出並移除該小團隊最前面的成員：`cout << team[front_team].front(); team[front_team].pop();`。

  * **關鍵判定**：如果該成員出隊後，導致該小團隊**已經沒有任何人在排隊了**（`team[front_team].empty()`），代表這個團隊在場上已徹底解散。此時必須將該團隊 ID 從主佇列中移除：`main.pop()`，讓後面的其他團隊遞補上來。


## 複雜度分析

* **時間複雜度**： $\mathcal{O}(N \log M)$ 或近乎 $\mathcal{O}(N)$ <br>
  其中 $N$ 為操作指令總數， $M$ 為相異成員的總數量。在入隊時，透過 `std::map` 查詢成員的團隊 ID 耗時 $\mathcal{O}(\log M)$。後續對 `main` 佇列與 `team[]` 佇列執行的 `push`, `pop`, `front` 操作皆為 $\mathcal{O}(1)$ 的常數代價。因此總體時間複雜度非常高效，能完美在幾毫秒內極速通過評測。
* **空間複雜度**： $\mathcal{O}(M + T \times \text{AvgSize})$ <br>
  主要包含大小為 $M$ 的 `team_map` 映射表空間，以及總數為 $T$ 的小團隊佇列儲存空間。空間開銷與總成員數量呈完全的線性正比。


## 邊界條件與潛在陷阱

1. **團隊解散時的主佇列移除**：

   這是本題最核心的 Bug 衍生點。當一個成員透過 `DEQUEUE` 離開小團隊後，**必須立即檢查該小團隊是否空了**。如果是，必須同步執行 `main.pop()`。如果漏掉了這一點，主佇列會殘留一個已經空掉的團隊 ID，在下一次 `DEQUEUE` 時會嘗試去讀取一個空的 `team[front_team].front()`，引發 SegFault 崩潰。

2. **多組測資間的空行格式要求**：

   題目嚴格規定：「每組 Scenario 的輸出結果之間」必須精確夾帶一個空行。這意味著**最後一組 Scenario 的結尾後面絕對不能殘留多餘的空行**。<br>
   原本程式碼末尾直接在 `while` 內部輸出 `cout << "\n"` 的寫法，會導致最後一個 Case 印完後屁股多留一個空行。**最穩健的作法是套用 `isFirst` 旗標控制，或在每組 Case 開始前（除第一組外）補換行**。

3. **陣列維度安全邊界**：

   題目表明團隊總數 $T \le 1000$。原程式碼中宣告 `queue<int> team[1005];`，預留了 5 個欄位的安全防禦空間，完全避免了陣列越界的風險。


## 程式碼實作

```cpp
#include <iostream>
#include <map>
#include <queue>
#include <string>
using namespace std;

int main() {
    // 提升標準 I/O 串流之效能
    ios::sync_with_stdio(false);
    cin.tie(0);
    
    int t;
    int count = 1; // 用於紀錄當前的 Scenario 編號
    
    // 連續讀入團隊數 t，當 t = 0 時安全結束程式
    while (cin >> t && t != 0) {
        
        // 雜湊映射表：成員編號 -> 團隊 ID
        map<int, int> team_map;
        
        for (int i = 0; i < t; i++) {
            int n;
            cin >> n; // 讀取該團隊的成員總數
            for (int j = 0; j < n; j++) {
                int m;
                cin >> m;
                team_map[m] = i; // 綁定對應關係
            }
        }
        
        // 嚴格依照題目規範輸出 Scenario 標頭
        cout << "Scenario #" << count++ << "\n";
        
        queue<int> main_queue;      // 主佇列：管理目前場上有哪些團隊 ID 在排隊
        queue<int> team_queue[1005]; // 佇列陣列：管理每個小團隊內部的實體成員順序
        
        string cmd;
        // 持續讀取指令，直到讀到 "STOP" 時代表該輪 Scenario 結束
        while (cin >> cmd && cmd != "STOP") {
            if (cmd == "ENQUEUE") {
                int x;
                cin >> x;
                int teamID = team_map[x]; // 在 O(log M) 內快速抽離出所屬小隊
                
                // 核心雙層轉移：若該小團隊目前在場上沒有任何隊友
                if (team_queue[teamID].empty()) {
                    main_queue.push(teamID);      // 該團隊 ID 必須至主佇列後方註冊掛號
                    team_queue[teamID].push(x);   // 成員推入小團隊內部
                }
                // 若場上早已有隊友在排隊，直接享有插隊權利，推入小隊末尾即可
                else {
                    team_queue[teamID].push(x);
                }
            }
            else if (cmd == "DEQUEUE") {
                // 優先鎖定目前排在整個隊伍最前端的團隊 ID
                int front_team = main_queue.front();
                
                // 輸出並彈出該團隊最前方的成員
                cout << team_queue[front_team].front() << "\n";
                team_queue[front_team].pop();
                
                // 核心關鍵防禦：若該成員離開後導致該小隊完全清空，主佇列必須同步註銷該團隊 ID
                if (team_queue[front_team].empty()) {
                    main_queue.pop();
                }
            }
        }
        // 核心格式控制：每組測試資料結束後都必須補上一個空行
        cout << "\n";
    }
    return 0;
}
```


## 進階優化思考
原做法使用 `std::map` 配合雙層佇列在時間複雜度上已非常優異。但在資工的頂級常數時間調優（Constant-time Optimization）視角下，存在一個能將時間複雜度直接壓低到絕對 $\mathcal{O}(1)$ 常數，且大幅減少陣列宣告體積的終極優化策略。
1. **陣列直尋雜湊化（Direct-Addressing Table, $\mathcal{O}(1)$ 查詢）**

   * **原理**： `std::map` 底層是紅黑樹，每次查詢 `team_map[x]` 耗時 $\mathcal{O}(\log M)$。如果題目給定的成員編號 $x$ 的範圍是已知的（例如 $x < 1,000,000$）。

   * **做法**：可以直接宣告一個全域的一維整數陣列 `int element_to_team[1000000];` 。在讀入數據時，直接以 `element_to_team[m] = i;` 填入。後續查詢時，直接透過下標 `element_to_team[x]` 一步到位。這能將成員辨識時間強制推向最極致的 $\mathcal{O}(1)$。

3. **鏈結串列指標模擬（Linked-List Queue / Pointer Optimization）**

   * **原理**：原本的做法宣告了 `queue<int> team[1005];` ，這等同於在記憶體中一次開闢了 1000 個獨立的雙端佇列物件。這在某些嵌入式或記憶體受限系統中是不夠優雅的。

   * **做法**：可以改用一個全域的雙向鏈結串列（ `std::list` ）來維護整個排隊隊伍。同時維護一個指標陣列 `Node* team_tail[1005];` ，用來儲存每個團隊當前排在隊伍中最尾端的那個人在鏈結串列中的實體記憶體地址（指標）。
  
     * 新成員 ENQUEUE：直接查找 team_tail[teamID]。若指標不為空，直接在該指標後方執行鏈結插入（insert），並更新指標；若為空，則直接推入鏈結串列的總末尾。

   * **優點**：此方法將整個系統簡化為單一條鏈結跑道，空間利用率達到了完美的 100%，且所有操作在底層全是指標的移位，能將記憶體零碎配置的開銷徹底抹除，是實現極限效能調優時非常高階的核心策略。
